Architecture

This guide includes source and direct-edition features. Check the edition comparison for the first Store release. Compare editions.

SEAL keeps its primary workspace on your machine. The desktop app, source MCP server, and Rust CLI can work against the same SQLite file, while each surface uses the execution engine appropriate to it.

Local-first by default

There is no required SEAL cloud workspace. The desktop app, CLI, and MCP server can read and write a single SQLite database on your machine. Network access happens only after an explicit outbound action, such as fetching from NCBI or UniProt, requesting an EBI or biohub.ai prediction, using an external model provider, or running an external agent. See Privacy for the complete boundary.

Native builds store data in the platform application-data directory, so your SQLite workspace is separate from any browser profile.

The surfaces

Three surfaces can share one workspace when they resolve the same database path. You can move between them, and a committed change made through one becomes visible to the others through the shared database and live-sync layer.

Desktop app

An Electron and React interface for reading, editing, and annotating sequences, with digest, primer design, assembly, alignment, and Activity records for workspace changes.

seal CLI

A Rust-native command-line tool for analysis, transformation, retrieval, and selected workspace operations. It is independently implemented and tested for explicit parity where the surfaces overlap. See the CLI reference.

MCP server

A source-checkout TypeScript Model Context Protocol server with 61 tools for analysis, transformation, cloning, IO, and workspace work. It is not bundled into the installed desktop app. See MCP setup and the MCP tool reference.

The shared workspace

State lives in a SQLite database. Commands that read or write shared data (blocks, conversations, features, projects, checkpoints, exports) resolve the database path in this order:

  1. SEAL_DB_PATH if set. An absolute path is recommended; a relative path is resolved against the current directory.
  2. A repo-local .seal/seal.db in the nearest parent directory that contains package.json or .git. Packaged desktop builds skip this lookup.
  3. The platform application-data directory, such as ~/Library/Application Support/io.github.jvogan.seal/seal.db on macOS.

Set SEAL_DB_PATH to a scratch file to isolate agent or test work from your live workspace. For example, export SEAL_DB_PATH=$(mktemp -d)/demo.db before a recording or a CI run.

Execution engines and parity

The desktop and MCP surfaces implement their broad operation set in TypeScript. The packaged app can route six bounded operations through native Rust commands: restriction-site search, ORF search, GC windows, Needleman-Wunsch alignment, inverted-repeat search, and repeat search. Browser fallback uses the TypeScript worker path. The seal CLI is a separate Rust-native implementation.

Shared command names do not by themselves promise byte-for-byte identity. SEAL pins parity with focused cross-runtime tests and documents known boundaries, such as the CLI primer command's legacy end-anchored algorithm versus the desktop and MCP flanking-region workflow.

Agents over MCP

External agents such as Claude Code, Codex, and Gemini CLI connect to the MCP server and operate on the same workspace through explicit tools. Activity records each write alongside changes made in the desktop app. See the agent control plane for setup and behavior.
