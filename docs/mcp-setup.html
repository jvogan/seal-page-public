MCP setup

This guide covers source and direct-edition tools. These tools are not bundled with the first Store release. Compare editions.

Connect an MCP client to the workspace you use in SEAL. The client runs a local server from your source checkout.

MCP is optional. Install SEAL and open the app before connecting a client.

Prepare the checkout

Use a SEAL checkout from a repository you have access to. Select the Node.js version in .nvmrc, then install the locked dependencies:

cd /absolute/path/to/seal
npm ci
npm run agent:doctor

The installed app does not bundle the source MCP runtime. Your client starts mcp/server.ts through the checkout's node_modules/.bin/tsx. The server communicates over stdio.

If the server fails to start, run npm ci in the source checkout and verify both absolute paths. Avoid npx so startup never depends on registry resolution or an unpinned download.

Configure a client

A client launches the server itself, so the configuration is a command plus its arguments and environment. The JSON configuration is what Claude Code (in .mcp.json) and Gemini CLI (in ~/.gemini/settings.json) use: a seal-bio entry under mcpServers that points at your checkout and sets SEAL_DB_PATH to the database you want the agent to share. Codex takes the same command, arguments, and environment, but as a TOML [mcp_servers.seal-bio] table. The per-client pages give the exact file and the mcp add command for each tool.

{
  "mcpServers": {
    "seal-bio": {
      "command": "/absolute/path/to/seal/node_modules/.bin/tsx",
      "args": ["/absolute/path/to/seal/mcp/server.ts"],
      "env": {
        "SEAL_DB_PATH": "/absolute/path/to/active/seal.db"
      }
    }
  }
}

Replace /absolute/path/to/seal with your checkout path and /absolute/path/to/active/seal.db with the active path from SEAL. The app's Agent Setup panel can copy a configuration with the database path filled in. For the exact config file and per-client steps, see Connect Claude Code, Connect Codex, and Connect Gemini CLI.

Share a workspace

The server resolves its SQLite database path in this order:

  1. SEAL_DB_PATH if set. Use this in scripts and config files.
  2. A repo-local .seal/seal.db, found by walking up from the working directory to the nearest package.json or .git.
  3. The OS application-data directory, such as ~/Library/Application Support/io.github.jvogan.seal/seal.db on macOS.

To share data with the running app, copy its active database path from Agent Setup into SEAL_DB_PATH. Set that path in every MCP or CLI process that uses the workspace. The app watches the database and refreshes after external writes.

Setting SEAL_DB_PATH explicitly keeps a client from writing to a repo-local development database while the installed app reads the app-data database. See Architecture for how the workspace is shared across surfaces.

Verify

In SEAL, run Agent Doctor from Agent Setup or the command palette. It confirms the active database path, file watcher, schema, and Activity hydration. A missing database path blocks setup. No recent external write is expected until the first MCP write.

Open a client session and ask it to call block_list. Compare the returned blocks with SEAL. This tool reads blocks across shared projects and Entries; workspace_list lists only MCP Scratch records.

Use block_list to list the sequence blocks in my SEAL workspace, with type and length. Do not change any data.
