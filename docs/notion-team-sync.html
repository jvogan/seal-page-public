Notion Team Sync

This guide covers source and direct-edition tools. These tools are not bundled with the first Store release. Compare editions.

Notion Team Sync is optional developer tooling for printing and validating a proposed ten-database contract. The checked-in alpha does not publish or synchronize SEAL records. Normal SEAL use does not require Notion.

The checked-in alpha validates a Notion workspace against the schema contract and exercises the local order-release policy. Report publishing, request-queue sync, provisioning, OAuth install, and bidirectional sync are planned, not shipped. Running the schema doctor is explicit and optional; local-only projects behave exactly as before.

What the alpha validates

SEAL remains a local-first sequence workbench. The current alpha can print the proposed Team Sync schema, check an already provisioned Notion workspace against that schema, and run the order-release policy locally. It does not turn Notion into a working shared registry.

The proposed contract reserves databases and fields for a future workflow covering:

  • shared project and sequence records visible in Notion
  • immutable sequence versions with content hashes and artifact pointers
  • request queues for work to run in SEAL
  • review gates before a version becomes the shared current version
  • order handoff gated on approval and the exact sequence hash
  • verification records for digest, colony PCR, Sanger, or NGS evidence
  • conflict rows in place of silent overwrites

Those bullets describe the contract under validation, not shipped data movement. The alpha does not create these databases, publish reports, process requests, or synchronize sequence versions.

The schema contract

The Notion side is a parent page that holds ten databases. The reusable contract lives in src/notion/team-sync-schema.ts, and the CLI reads that module rather than a hand-maintained property list. Print the expected contract:

npm run dev:cli -- notion schema

The ten databases:

DatabaseRole in the proposed contract
SEAL ProjectsFuture shared project records.
SEAL SequencesStable sequence records that point to the current version, not editable raw sequence fields.
SEAL Sequence VersionsImmutable versions with a SHA-256 and artifact pointers.
SEAL RequestsExecutable work requests created by Notion users.
SEAL RunsAnalysis and automation records.
SEAL ReportsPublished report packages and validation artifacts.
SEAL ReviewsHuman review gates for versions and reports.
SEAL Order HandoffVendor and order rows gated by review and hash checks.
SEAL Verification Resultsexperimental or sequencing evidence linked to exact versions.
SEAL Sync ConflictsExplicit conflict queue for divergent local and remote versions.

The proposed design keeps raw sequence text out of editable Notion fields. Its schema expects display metadata, version rows, content hashes, artifact links, and review state while raw FASTA, GenBank, report packages, and manifests remain in SEAL or controlled artifact storage. The current alpha validates that shape only; it does not create version rows or move artifacts.

CLI tooling

The alpha surface is three commands. notion schema prints the expected database contract, and notion doctor validates a live Notion workspace against it. Point the doctor at a local IDs file that maps the ten database IDs to the stable schema keys.

npm run dev:cli -- notion doctor --ids-file .seal/notion-team-sync-ids.json --json

A passing workspace returns:

{
  "ok": true,
  "checkedDatabases": 10,
  "issues": []
}

The doctor needs a Notion internal connection with read content access, shared with the parent page, plus the database IDs. Start from the placeholder shape and fill in the real IDs:

mkdir -p .seal
cp docs/notion-team-sync-ids.example.json .seal/notion-team-sync-ids.json

Put the token in the current shell without writing it to command history:

read -rsp "Notion token: " SEAL_NOTION_TOKEN
export SEAL_NOTION_TOKEN
printf "\n"

Keep tokens and database IDs out of the repo, shell history, CI logs, and demos. Use the IDs file (or SEAL_NOTION_TEAM_SYNC_DB_IDS_FILE pointing at it) and the placeholder docs/notion-team-sync-ids.example.json for local config.

Order-release policy smoke test

The order-release policy decides when an order row may move to Ready for order. The reusable module is src/notion/team-sync-policy.ts, and a local smoke test exercises it without touching Notion:

npm run notion:team-sync:smoke

The smoke test covers these cases:

  • an open review blocks order release
  • an open sync conflict blocks order release
  • a review hash mismatch blocks order release
  • a superseded version blocks order release
  • missing required vendor fields block order release
  • an approved, hash-matched, conflict-free order becomes Ready for order
  • repeated policy evaluation is deterministic

The policy result collects every visible blocker for a future Notion Block Reason field, and the local smoke test verifies that behavior without writing to Notion. The same schema-doctor path is also available as npm run notion:team-sync:doctor.

Status

This page documents the alpha. The contract, doctor, and order-policy smoke test are checked in. The following are planned and are not public release promises yet:

  • provisioning the Notion workspace from SEAL (future seal notion init)
  • publishing report packages into Notion (future seal notion publish-report)
  • processing Notion request queues (future seal notion sync-once and watch)
  • background watch and webhook sync
  • a public OAuth connection and a Notion Custom Agent

The bare seal notion ... forms above are future production CLI shapes. The checked-in commands today live in the development TypeScript CLI under npm run dev:cli.
