Prompts and safety

This guide covers source and direct-edition tools. These tools are not bundled with the first Store release. Compare editions.

Safety prompts and review patterns for agent edits. Use these with Claude Code, Codex, Gemini CLI, or any other MCP-capable local agent working in your SEAL workspace.

Before you hand off

Get the workspace ready, then ask for a read-only pass before any write.

  1. Open SEAL and go to Start Panel, then Agent Control Plane.
  2. Copy the active SQLite database path or the MCP config snippet.
  3. Run Agent Doctor and fix any failed database path check before asking the agent to write.
  4. Tell the agent to use the configured SEAL MCP server, or the Rust seal CLI with the same SEAL_DB_PATH.
  5. Ask for a read-only inventory first. Move to writes only after the agent has named the target blocks, projects, or conversations.

For the config itself, see MCP setup and the per-client pages: Claude Code, Codex, and Gemini CLI.

Safe starter prompt

Paste this at the start of an agent session. It sets the read-first order, the confirmation rule for destructive edits, and the summary an agent should return after every write.

You are working with SEAL through the configured SEAL MCP server or Rust seal CLI.

Use the active SQLite workspace only. Start read-only: use block_list to inventory shared sequence blocks, then list projects, conversations, and recent Activity. Then propose a short plan before writing.

Do not delete, overwrite, rename, reorder, or mutate existing blocks unless I explicitly confirm the target and action. Before destructive edits, create or identify a checkpoint. After every write, summarize the affected block names, IDs when available, write source, and any warnings I should verify in SEAL Activity.

Review patterns

Two surfaces let you review what an agent did and recover from it: the Activity trail and checkpoints.

Activity trail

Activity records external writes alongside changes made in the desktop app. Each mutation records its source (writeSource is mcp or cli), the tool or command name, and the affected project, conversation, and block IDs in structured metadata. Collapsed rows use block names and source labels; raw IDs remain in the metadata for debugging and export round trips.

Ask the agent to end each write with a summary you can check against Activity: affected block names, IDs when available, the write source, and any warnings. Then confirm in SEAL that the source label and target names match what you expected.

Checkpoints

Before a destructive edit, have the agent create or identify a checkpoint so a recoverable change can be restored. Where a checkpoint would cascade away with the thing being deleted, SEAL records a metadata snapshot instead. The behavior is per operation; see what agents can change for the checkpoint result of each mutation.

Guardrails

Agent writes go directly into SQLite. SEAL does not put them behind an approval queue; it makes them observable and recoverable instead. Hold the agent to these norms:

  • Read before write. Require a read-only inventory and a short plan before any mutation. Writes start only after the agent names its targets.
  • Confirm destructive actions. Do not let the agent delete, overwrite, rename, reorder, or mutate existing blocks, or delete a conversation, without your explicit confirmation of the target and the action.
  • Checkpoint first. Before a destructive edit, create or identify a checkpoint, or capture a snapshot where a checkpoint cannot survive the deletion.
  • Summarize and verify. After each write, get the affected names, IDs, write source, and warnings, and verify them in Activity.
  • Stay on the intended workspace. Confirm the agent uses the same database path shown in Agent Setup. To keep agent or test work off your live workspace, set SEAL_DB_PATH to a scratch file first.

Prompt pack

Copyable prompts for common requests. Each one keeps the read-first, confirm-before-write order.

Inventory the workspace

Use SEAL MCP/CLI read-only tools to inventory my current workspace. List sequences, projects, conversations, feature counts, topology, and any obvious metadata gaps. Do not write yet. End with the next safest actions.

Import and inspect a sequence

Import the attached or referenced FASTA/GenBank record into SEAL. Preserve source metadata, topology, features, and provenance where possible. After import, inspect length, GC, ORFs, restriction sites, feature coordinates, and parse warnings. Do not mutate the sequence. Summarize what changed and what I should verify in Activity.

Plan a restriction digest

For the active SEAL block, plan a restriction digest and verification workflow. Show candidate enzymes, expected fragments, unique-site risks, methylation or ambiguity issues if detectable, and a gel/checkpoint plan. Do not add or edit features until I confirm the enzymes and target block.

Add verified restriction features

Using the confirmed target block and enzyme list, find restriction sites and add feature annotations for the verified sites only. Keep feature names readable, preserve exact coordinates, and summarize every added feature with start/end, strand, and affected block ID.

Design primers with scope

Design primers for the active SEAL block or selected range. State assumptions, target coordinates, expected product size, Tm/GC ranges, tails or overhangs, and any off-target or ambiguity risks. Do not write primer features or mutate the block until I confirm the design.

Prepare a report

Build a SEAL report plan for this conversation. Include selected blocks, provenance, analysis status, warnings, lossy export notes, suggested attachments, and the Activity events or block IDs that support each result.

Review failed writes

Review failed, partial, or blocked external-agent writes in this SEAL workspace. Explain what was attempted, what changed, what did not change, affected blocks, available checkpoints, and the safest retry or recovery path.

Choosing MCP or CLI

Both paths write to the same SQLite database when SEAL_DB_PATH is set correctly, and both appear in Activity with their write source.

  • Use MCP when the agent is already reasoning over the workspace and should call structured tools such as block_list and block_get, parse_sequence, restriction_sites, feature_add, checkpoint_save, and the export tools.
  • Use the Rust seal CLI when the work is script-like: batch imports, shell pipelines, repeatable checks, or commands that should be easy to paste into a terminal.

What to verify in SEAL

After an agent works, check these in the app:

  • The agent used the same database path shown in Agent Setup.
  • The target block, project, and conversation names match what you expected.
  • Activity shows the external write source after MCP or CLI writes.
  • Checkpoints exist before destructive edits.
  • Imported features stay within sequence bounds and use the expected topology.
  • Exports mention any lossy format limitations.
