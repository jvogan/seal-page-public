Security

This guide includes source and direct-edition features. Check the edition comparison for the first Store release. Compare editions.

SEAL stores its primary workspace on device. It isolates renderer code, validates IPC messages, and limits subprocesses. Local unsigned builds use ad-hoc signing and disable in-app provider-key storage.

Electron production fuses

SEAL configures seven production Electron fuses on the packaged bundle. Fuses are configuration flags written to the Electron binary during packaging. These settings disable default Node.js features to reduce the runtime attack surface.

Electron Fuse Production State Description
RunAsNode Disabled Prevents executing arbitrary scripts through the binary using command-line arguments.
EnableCookieEncryption Enabled Encrypts local cookies stored on disk using OS-level cryptographic keys.
EnableNodeOptionsEnvironmentVariable Disabled Ignores the NODE_OPTIONS environment variable to prevent injection of scripts or preloads.
EnableNodeCliInspectArguments Disabled Disables CLI flags like --inspect to block attaching debuggers to the packaged application.
EnableEmbeddedAsarIntegrityValidation Enabled Verifies the cryptographic integrity of the application ASAR archive during start-up.
OnlyLoadAppFromAsar Enabled Restricts resource loading to files located within the read-only packaged ASAR archive.
GrantFileProtocolExtraPrivileges Disabled Revokes legacy directory permissions from the file:// protocol. Packaged assets load from the restricted app:// protocol.

Process isolation and IPC control

The desktop application runs the user interface inside a sandboxed renderer process with context isolation. System operations are mediated by the main process through Inter-Process Communication (IPC).

The main process enforces two layers of validation on every IPC message:

  • Trusted-sender verification. The main process verifies the identity of the sending web frame. Both the top-level WebContents URL and the sending frame URL must match the canonical production URL (app://seal/dist-electron/renderer/index.html) or the authorized localhost dev URL during development. Process and routing IDs are checked against main-process records.
  • Two-tier command allowlist. IPC requests must resolve to a valid command on the allowlist. RENDERER_NATIVE_COMMANDS defines the allowed native functions the renderer is permitted to call. Privileged functions like secure_get_key belong to MAIN_PROCESS_ONLY_NATIVE_COMMANDS. These functions are blocked from renderer IPC requests. Legacy data mutations are explicitly blocked by the main process.

Subprocess execution policy

The two external multiple sequence alignment tools, MUSCLE and Clustal Omega, run in dedicated subprocesses. The main process constrains these child processes using several security boundaries:

  • No shell interpolation. Subprocesses are spawned using execFile with the shell option set to false. Arguments are passed exclusively as an array of literal strings to prevent argument injection.
  • Allowlisted executables. Only supported engines with validated paths and version signatures are executed. Path components and filenames are checked against the manifest.
  • Sanitized environment variables. The process environment of the child is stripped. Only basic paths, HOME, TMPDIR, and standard locale variables are populated.
  • Private temporary directories. Subprocess inputs and outputs are written to a unique directory created via fs.mkdtemp with restricted (0o700) permissions. Input files are written with 0o600 permissions. The directory is recursively deleted upon completion or execution failure.
  • Bounded resource usage. Input sequence payloads are capped at 1,000 sequences, 1,000,000 bytes per sequence, and 8,000,000 bytes in aggregate. Output streams and files are read up to a verified limit of 64 MiB for alignments and 1 MiB for diagnostic logs.
  • Timeouts and cancellation. Child processes are bounded by a default timeout of 10 minutes (600,000 ms), which callers can override. Execution can be aborted at any point using an AbortController signal, which terminates the child process.

Content Security Policy and proxies

The application enforces a Content Security Policy (CSP) on the default session during runtime:

default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; worker-src 'self' blob:; connect-src 'self' https://api.openai.com https://api.anthropic.com https://generativelanguage.googleapis.com https://api.moonshot.cn https://eutils.ncbi.nlm.nih.gov https://rest.uniprot.org

Renderer connections are restricted to allowed hostnames, including NCBI E-utilities, UniProt, and configured LLM providers (OpenAI, Anthropic, Google Gemini, and Moonshot).

Certain integration services, such as the European Bioinformatics Institute (EBI) protein annotation service and the biohub.ai model logits service, do not serve CORS headers. Direct browser-level connections are blocked by Chromium. These integrations use HTTP proxies in the Electron main process. The biohub.ai proxy reads the configured provider key from secure storage and attaches it to the request. Because proxy requests originate from the main process, they are not governed by the renderer's CSP. The proxies implement destination filters. The EBI proxy only allows Phobius and InterProScan endpoints, and the biohub.ai proxy only permits ESM model logits requests. Concurrency gates limit active requests to prevent resource exhaustion.

Workspace storage and data locations

Workspace state, including conversations, sequence blocks, and activity metadata, is stored in a local SQLite file named seal.db. The database path is resolved using the following order of precedence:

  1. The SEAL_DB_PATH environment variable, if set.
  2. A repo-local seal.db inside .seal/ if a repository root is found. This check is skipped in packaged production builds.
  3. The platform-native application data directory:
    • On macOS: ~/Library/Application Support/io.github.jvogan.seal/seal.db
    • On Windows: %APPDATA%\io.github.jvogan.seal\seal.db
    • On Linux/BSD: ~/.local/share/io.github.jvogan.seal/seal.db

Electron uses a separate userData tree, typically ~/Library/Application Support/SEAL/ on macOS, for window-state.json, Chromium profile data, and secure-keys.json. It is not the SQLite bundle-id directory.

When OS-backed storage is available, Electron safeStorage encrypts hosted sequence-model keys using macOS Keychain. The resulting ciphertext is written to secure-keys.json in that separate userData directory, and decryption happens in the main process. Legacy-compatible provider keys can instead be persisted in SQLite only when explicitly enabled.

macOS builds and credentials

The local unsigned package is ad-hoc signed for code integrity. It has no Developer ID signature or notarization ticket. If macOS blocks its first launch, follow the installation instructions.

This package disables in-app provider-key storage and preserves existing encrypted key files. External agents and terminal tools use their own credential stores. Source development runs can use hosted models when OS-backed secure storage is available.

Developer ID signing and notarization are a separate direct-download option. The Mac App Store edition is planned. See installation options for availability.
